# 项目开发底座跨仓库交付审查

从产品行为到三个 Git 仓库审查项目服务功能是否真正完整交付。当前主要项目服务是应用版本管理中心（AVMC）。

## 审查原则

- 先报告缺陷、回归、缺失测试和交付风险，再总结修改内容。
- 所有发现必须包含具体文件和行为影响。
- 不因代码存在就判断功能完成；必须验证契约、权限、测试和交付状态。
- 不修改或撤销用户已有的无关改动。

## 读取范围

开始前读取：

1. `.codex/AGENTS.md`
2. `.codex/RULES.md`
3. `.codex/DESIGN.md`
4. `docs/architecture/README.md`
5. `docs/services/README.md`
6. 相关 `docs/product` 当前需求
7. 目标功能的后端 Proto 和实现
8. 目标功能的前端 API、页面、路由和 locales

历史文档仅用于追溯，不作为当前实现事实来源。

## 审查步骤

### 1. 建立需求与验收映射

明确：

- 功能目标、角色和业务结果
- 正常流程和失败流程
- 权限与项目数据边界
- 状态转换和破坏性操作
- 可验证验收标准

需求存在重要歧义时，将其作为风险报告，不静默假设。

### 2. 检查前后端契约一致性

检查：

- Protobuf 字段与前端 API 类型、请求参数、表单字段和展示字段是否一致
- 枚举、状态、分页、过滤和排序语义是否一致
- 错误行为是否能被前端正确处理
- 前端是否暴露后端不支持的操作
- 后端新增能力是否缺少前端入口或产品文档说明

### 3. 检查后端完整性

沿以下链路检查：

`proto -> generated API -> service -> biz/usecase -> data/repo -> Ent schema -> Wire/server`

重点检查权限、项目隔离、校验、唯一性、状态冲突、事务、生成来源和测试覆盖。

### 4. 检查前端完整性

沿以下链路检查：

`route/menu -> view -> data.ts -> modules -> api -> locales`

重点检查权限、加载/空数据/错误状态、破坏性确认、状态刷新、中文和英文文案、类型检查及测试覆盖。

### 5. 检查交付状态

分别执行并审查：

```bash
git status --short
git -C backend-service status --short
git -C frontend-service status --short
git submodule status
```

确认：

- 后端代码修改应在 `backend-service` 内提交
- 前端代码修改应在 `frontend-service` 内提交
- 根仓库仅承载根级文件、文档和子模块指针
- 子模块指针不能指向未提交或错误提交
- 不应包含无关生成文件或构建产物

### 6. 检查验证证据

根据改动确认相关检查已经执行：

- 后端测试
- Buf lint/breaking
- 前端 typecheck/build
- 前端单元测试或 E2E 测试
- UI 行为验证

缺少关键验证时，将其报告为交付风险。

## 输出格式

按严重程度输出发现：

1. 阻止功能正确交付的问题
2. 权限、安全、数据隔离或兼容性风险
3. 行为回归和测试缺口
4. 文档、生成或子模块交付问题

每项发现包含：

- 严重程度
- 文件和位置
- 具体问题
- 用户或系统影响
- 建议修复方向

没有发现问题时，明确说明未发现问题，并列出尚未执行的测试或剩余风险。
