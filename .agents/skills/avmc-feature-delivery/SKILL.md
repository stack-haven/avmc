# Ark Tech Platform 产品服务功能交付

通过需求优先、契约驱动的工作流交付产品服务功能。保证实现符合仓库当前规则，并为每一项验收标准提供验证证据。

## 启动前确认

与调用方确认以下信息：

1. 目标服务/应用及功能范围
2. 活跃服务或应用中最接近的现有实现（作为模板参考）
3. 涉及的 Proto 契约、Ent schema、前端路由范围

## 选择交付模式

- 用户要求先分析后确认时，完成现状发现、歧义分析、影响矩阵和建议验收标准；停止在文件修改之前，等待用户确认。
- 用户要求实现时，完成从分析到验证的完整工作流。
- 用户要求审查时，将发现映射到需求和验收标准；优先报告缺陷、回归、测试缺口和未解决的需求歧义。

## 交付工作流

### 0. 确认功能清单（必须）

**每次开发前必须先执行此步骤。** 功能清单是开发计划与代码实现之间的桥梁，确保不遗漏、不重复、不偏离。

1. **加载清单**：读取 `docs/architecture/4-7-治理-代码功能清单.md`

2. **匹配功能**：在当前清单中查找目标功能：
   - 已存在且状态为 `[x]` → 报告"该功能已完成"，询问是否要修改/扩展
   - 已存在但状态为 `[ ]` 或 `[.]` → 确认是否启动
   - 已存在但范围不匹配 → 与用户确认调整范围
   - 不存在 → 在清单中追加新行

3. **确认范围**：将清单中匹配的功能行展示给用户确认：
   ```
   确认以下开发范围：
   | 状态 | 优 | 功能 | 描述 |
   | [ ] | P1 | 你的新功能 | 功能描述 |
   
   是否按此范围开发？如有调整请说明。
   ```

4. **人工调整**：用户可以通过以下方式调整清单：
   - 修改功能描述 — 直接编辑对应的行
   - 调整优先级 — 修改 `P0/P1/P2/P3`
   - 拆分功能 — 将一行拆为多行
   - 合并功能 — 将多行合并为一行
   - 删除功能 — 标记为 `[.]` 暂缓
   - 新增功能 — 在对应模块下追加新行

5. **锁定范围**：用户确认后，将目标功能标记为 `[~]`（进行中），然后进入正式开发流程。

**清单格式速查：**
```markdown
| 状态 | 优 | 功能 | 描述 | 源码追溯 |
|:---:|:---:|------|------|------|
| [x] | P0 | 已完成功能 | 描述 | `proto/file.proto` `service.go` |
| [~] | P1 | 进行中功能 | 描述 | — |
| [ ] | P2 | 待开发功能 | 描述 | — |
| [.] | P3 | 暂缓功能 | 原因: xxx | — |
```

状态标记：`[x]` 已完成 | `[~]` 进行中 | `[ ]` 待开发 | `[.]` 暂缓
优先级：P0(必须) / P1(当前迭代) / P2(下一迭代) / P3(远期)
源码追溯：记录实现该功能的 Proto、Service、UseCase、Schema 等文件路径

### 1. 明确需求

将功能需求重述为可执行内容：

- 用户或角色
- 目标和业务结果
- 范围内行为
- 明确的非目标
- 权限和项目数据边界
- 生命周期状态和状态转换
- 失败、空数据、加载中和破坏性操作行为

识别用户请求、当前产品文档和代码之间的冲突。不得静默处理会影响产品行为的重要歧义。仅当合理假设可能导致实现错误时向用户确认。

### 2. 检查现有能力

提出修改方案前，定位最接近的现有实现模式。

后端任务检查以下链路：

`backend-service/proto -> backend-service/api -> internal/service -> internal/biz -> internal/data -> internal/data/ent/schema`

前端任务检查以下链路：

`router -> views -> data.ts -> modules -> api -> locales`

记录已有能力、可复用内容和缺失内容。避免修改生成文件、备份代码、示例代码或无关的 Vben 应用。

### 3. 建立影响矩阵

使用 `references/delivery-checklist.md` 作为输出模板。将每个区域标记为：

- `required`：本次必须处理
- `not required`：本次无需处理
- `needs confirmation`：需要用户确认

在能够确定时填写准确目标路径。覆盖产品文档、API 契约、后端分层、持久化、权限、前端行为、i18n、测试、代码生成、CI 和子仓库交付。

### 4. 修改前定义验收标准

使用可观察行为编写可验证的验收标准。每项标准必须包含：

- 前置条件
- 执行动作
- 预期结果
- 验证方式

除正常流程外，根据功能需要覆盖权限拒绝、无效输入、状态冲突、破坏性操作确认和项目数据隔离。每项计划修改和测试至少关联一项验收标准。

### 4.1 明确列表接口边界

设计任何功能数据列表前，必须先区分列表页、详情页和选择器的真实数据需求：

- 列表接口只返回当前列表展示、筛选、排序和必要操作所需字段；不得为了复用详情模型，把详情字段、复杂关联、大文本、权限树或配置明细默认塞进列表响应。
- 详情页需要的完整字段走 `GetXxx` 或独立详情接口，不以列表接口承载详情数据。
- 表单下拉、绑定选择、轻量筛选等高复用场景，优先设计 `ListXxxSimple` / `ListXxxSimples` 类简单列表接口，响应字段限定为 `id`、显示名、状态、排序、父级等最小必要信息。
- 已有相邻实现优先参考 `ListUsersSimple`、`ListTenantSimples` 以及 role/menu/post/dept 的 `ListSimple` 用例；例如角色选择不应复用完整 `ListRoles`，应补齐 `ListRoleSimple` 或同项目命名风格的简单列表接口。
- 如果暂时复用完整列表接口，必须在需求文档和最终交付中说明原因、字段冗余影响和后续拆分条件。

### 5. 按依赖顺序实现

跨前后端功能默认按以下顺序实施：

1. 契约存在歧义时，澄清或更新当前产品文档。
2. 定义或更新 Protobuf 契约和校验规则。
3. 使用仓库命令生成 API 和 OpenAPI 输出。
4. 实现 Ent schema、repository、usecase、service、服务注册和 Wire 依赖。
5. 在行为附近添加后端测试。
6. 实现有类型约束的前端 API wrapper。
7. 实现路由、页面、schema、drawer/modal、权限和 locales。
8. 为重要行为添加前端单元测试或端到端测试。
9. 已交付行为改变产品定义时，更新当前产品文档。

仅当影响矩阵标记为 `not required` 时跳过对应步骤。

### 6. 根据影响矩阵验证

先运行范围最小且相关的检查，再根据风险扩大检查范围。

后端常用检查：

```bash
go test ./...
buf lint
buf breaking
```

前端常用检查：

```bash
pnpm -F @vben/web-antd-admin run typecheck
pnpm -F @vben/web-antd-admin run build
pnpm run test:unit
```

根据任务验证生成输出、中文和英文文案一致性、权限行为及 UI 行为。无法运行检查时，必须说明原因。

### 7. 更新功能清单

开发完成并验证通过后，必须更新功能清单：

1. 将目标功能的状态从 `[~]` 改为 `[x]`
2. 填写源码追溯列（Proto 文件、Service 文件、UseCase 文件、Schema 文件等）
3. 如果是新增功能，确认行格式与清单模板一致
4. 如果有未完成的部分，拆分为新行并标记为 `[ ]`

```markdown
# 更新前
| [~] | P1 | 新增通知渠道 | 支持邮件和短信通知 | — |

# 更新后
| [x] | P1 | 新增通知渠道-邮件 | SMTP 集成完成 | `proto/.../i_notification.proto` `notification_usecase.go` |
| [ ] | P2 | 新增通知渠道-短信 | 短信服务商集成待启动 | — |
```

### 8. 审计交付完整性

分别检查以下 Git 状态：

- 根仓库
- `backend-service`
- `frontend-service`

不得修改用户已有的无关改动。只有代码修改已提交到所属子仓库后，才能将根仓库子模块指针更新视为完整交付。

最终报告：

- 已实现行为
- 验收标准完成状态
- **功能清单更新状态**（新增/修改/完成的行）
- 已修改文件或分层
- 验证证据
- 未解决决策或剩余风险

## 强制约束

- `backend-service/app/platform/service` 默认承接平台基础能力；业务模块应先确认服务边界再决定代码落点。
- `frontend-service/apps/web-antd-admin` 作为管理后台前端默认开发目标。
- 后端 API 修改必须从 `backend-service/proto` 开始；不得手工修改生成的 API 或 Ent 文件。
- 优先复用现有 Vben CRUD 模式和公共消息，再考虑新增抽象。
- 新增可见 UI 文案时，同时添加中文和英文 locale。
- 破坏性操作和状态转换必须要求用户确认。
- 项目级数据隔离和权限必须由后端行为保证，不能只依赖 UI 隐藏。
- 必要测试、代码生成或子仓库交付未完成时，不得声称任务已完成。
