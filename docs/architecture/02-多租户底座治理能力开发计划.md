# 多租户底座治理能力开发计划

日期：2026-06-27  
状态：实施中  
范围：项目开发底座，不包含 AVMC 业务服务

## 1. 架构目标

多租户底座需要同时提供两类能力：

- 平台控制面：租户生命周期、业务套餐、平台配置、审计监管和资源治理。
- 租户数据面：组织、成员、角色、菜单、字典、租户配置及租户业务数据隔离。

所有新增项目服务必须复用租户上下文、权限、审计和配置机制，不得自行实现另一套租户识别或操作日志。

## 2. 架构原则

1. 后端强制隔离：租户边界由认证上下文、Ent policy 和 repository 查询共同保证。
2. 契约优先：API 先修改 `backend-service/proto`，再生成传输代码并实现 Kratos 分层。
3. 控制面显式授权：平台跨租户操作必须使用平台身份和显式目标租户，不能依赖普通租户管理员权限。
4. 审计不可变：操作日志只允许追加和查询，不提供修改、删除接口。
5. 配置可追踪：字典、参数、套餐等配置变更必须具备版本、缓存失效和审计记录。
6. 业务无关：底座只提供通用治理能力，不承载版本、发布、反馈等项目服务业务。

## 4. 第一阶段实施范围

### 4.1 数据字典

聚合：

- `DictionaryType`：字典类型，租户内 `code` 唯一。
- `DictionaryItem`：字典项，在字典类型内 `value` 唯一。

行为：

- 租户管理员维护本租户字典类型和字典项。
- 字典项支持标签、值、排序、颜色、状态和备注。
- 禁用字典类型后，其字典项不应作为有效业务配置使用。
- 已被业务引用的字典项删除保护在建立统一引用注册机制后实现。
- 平台字典模板采用“发布版本 -> 租户订阅/覆盖”模型，在平台身份模型完成后实现，首期不使用 `tenant_id = 0` 绕过隔离。

### 4.2 操作审计

聚合：

- `OperationLog`：追加写入的审计事件。

记录内容：

- 租户、操作人、模块、动作、资源类型和资源 ID。
- HTTP/gRPC operation、请求方法和路径。
- 请求参数摘要、变更前后差异。
- IP、User-Agent、Trace ID、执行结果、耗时和错误信息。

约束：

- 对外只开放列表和详情查询。
- 写入由底座内部 `OperationAuditRecorder` 统一完成。
- 密码、令牌、密钥、验证码等字段进入持久化前必须脱敏。
- 已提供记录器、查询闭环和 HTTP/gRPC 自动审计 middleware；中间件只覆盖受保护的写操作，读取操作不产生审计记录。

## 6. 第一阶段验收标准

- 同一租户不能创建重复字典编码。
- 不同租户可使用相同字典编码，且互相不可见。
- 字典项只能属于当前租户的字典类型。
- 审计日志不存在更新和删除 API。
- 普通租户只能查询本租户审计日志。
- 审计记录中的敏感字段已脱敏。
- 后端生成、编译和不依赖数据库的单元测试通过。
- 前端类型检查通过。
