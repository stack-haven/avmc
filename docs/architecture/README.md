## 使用规则

- 架构决策只能在本目录更新，不要散写到产品需求或旧归档文档中
- `docs/archive/` 中的历史架构描述只作参考，和本目录冲突时以本目录为准
- 新增模块须先通过 `4-1-治理-产品服务模块接入规范.md` 的清单评审
- 继续推进平台基础能力时，先读 `4-3-治理-能力路线图.md`，完成后更新断点和验收证据
- 每篇文档头部标注**状态**和**优先级**，防止"设计文档"被当成"实现要求"

### 文档保鲜规则

- 每次代码 PR 涉及架构变更时，检查对应文档是否需要更新
- 每季度检查一次文档中的文件路径引用是否仍然有效
- 文档中引用的 Git 分支、版本号、命令必须与当前 Makefile 和 CI 配置一致
- 状态为"设计阶段"的文档超过 6 个月未更新，标记为 `🔴 待复审`
- `4-3-治理-能力路线图`、`4-6-治理-开发功能清单` 和 `4-7-治理-代码功能清单` 必须在每个迭代完成后同步更新

## 当前冻结结论

- `backend-service/app/platform/admin` — 平台基础管理后台服务，不承载具体产品业务
- `backend-service/app/ai/service` — AI/chat 通用能力服务
- `backend-service/app/version/service` — 已冻结，恢复前必须复审
- 产品服务需先在 `docs/services` 定义边界，是否拆独立 service 须按拆分条件复审
