# 统一异步任务中心设计

日期：2026-07-01
状态：首期实施并通过真实环境验证
范围：项目开发底座通用后台任务，不包含业务服务专属任务逻辑

## 1. 目标

统一异步任务中心为套餐定时生效、通知投递、文件处理、批量导入导出、会话清理和后续业务服务提供可靠的后台执行底座。

首期解决：

- 任务持久化，服务重启后不丢失。
- 多实例通过数据库条件更新独占抢占任务。
- 执行租约过期后允许其他 worker 接管。
- 幂等键防止相同业务任务重复入队。
- 失败自动重试、指数退避和最大执行次数。
- handler panic 隔离，不导致服务进程退出。
- 平台管理员查询、取消待执行任务和人工重试失败任务。
- 平台管理员查看任务健康汇总，识别积压、失败、租约过期和重试压力。
- 终态任务按保留期批量清理。

## 2. 安全边界

管理 API 不提供创建任意任务接口，也不接受任务类型或原始 JSON 载荷。

任务只能由后端代码通过 `AsyncTaskUsecase.Enqueue` 入队，并且任务类型必须存在于 handler 注册表。该约束避免任务中心成为远程代码执行、任意内部接口调用或敏感载荷注入入口。

公开响应只返回 `payload_summary`，不返回原始 `payload`。任务生产方必须确保摘要不包含密码、令牌、密钥和个人敏感信息。

首期任务管理 API 属于平台控制面，普通租户管理员不能查询或操作全局任务。

## 3. 数据模型

`AsyncTask` 主要字段：

- `tenant_id`：可空；平台任务为空，租户相关任务保存真实租户 ID，不使用 `tenant_id = 0`。
- `task_type`：已注册 handler 类型。
- `queue`：逻辑队列。
- `status`：待执行、执行中、成功、失败或已取消。
- `payload`：内部 JSON 载荷，不通过管理 API 返回。
- `payload_summary`：可展示的脱敏摘要。
- `idempotency_key`：可空唯一键；持久化时自动增加 `platform` 或真实租户 ID 作用域，同一业务键可安全用于不同租户。
- `attempts` / `max_attempts`：执行次数和上限。
- `scheduled_at`：最早可执行时间。
- `lease_owner` / `lease_expires_at`：worker 租约。
- `result_summary` / `last_error`：执行结果和错误摘要。

索引覆盖：

- 状态、队列、计划时间和优先级。
- 状态和租约过期时间。
- 租户和创建时间。
- 任务类型和创建时间。

## 4. 状态机

```text
PENDING --claim--> RUNNING --success--> SUCCEEDED
   |                  |
   | cancel           | failure and attempts remain
   v                  v
CANCELED           PENDING
                      |
                      | attempts exhausted
                      v
                   FAILED --manual retry--> PENDING
```

规则：

- 只有 `PENDING` 可以取消。
- 只有 `FAILED` 可以人工重试。
- 人工重试清空执行次数、错误、完成时间和租约。
- `RUNNING` 且租约过期的任务可被其他 worker 重新抢占。
- 完成和失败更新必须同时匹配任务 ID、`RUNNING` 状态和租约持有者，旧 worker 不能覆盖新 worker 结果。

## 5. 执行模型

worker 作为 Kratos `transport.Server` 接入应用生命周期：

- 与 HTTP/gRPC 服务一起启动。
- 服务停止时接收统一停止信号。
- 每 500ms 轮询 `default` 和 `maintenance` 队列。
- 单轮每个队列最多处理 10 个任务，避免无限占用循环。
- 当前租约为 2 分钟，适用于首期短任务。
- 数据库轮询失败时按 1 秒到 30 秒指数退避，成功后恢复正常频率，避免故障期间放大连接压力和错误日志。

抢占采用数据库条件更新：

1. 查询已到计划时间的待执行任务，或租约已过期的执行中任务。
2. 按优先级、计划时间和 ID 排序。
3. 使用包含原状态条件的 `UPDATE` 抢占。
4. 只有更新行数为 1 的 worker 获得执行权。

该模式不依赖单进程内存锁，多实例可以共享同一任务表。

## 6. 重试与故障处理

- 自动重试采用 5 秒起步的指数退避，最大 5 分钟。
- 默认最多执行 3 次，允许范围为 1 到 10 次。
- handler panic 被恢复并按失败处理，同时记录堆栈日志。
- worker 或进程异常退出后，任务在租约过期后重新进入可抢占范围。
- 数据库不可用时不确认任务成功，恢复后继续执行。

幂等键只能防止重复入队，handler 仍必须针对外部副作用设计业务幂等。例如通知投递、文件转换和套餐发布应使用业务唯一键或状态条件更新。

## 7. 首期内置任务

`system.task_retention_cleanup`：

- 每个自然日使用日期幂等键确保只创建一次。
- 清理指定保留期之前的成功、失败和取消任务。
- 默认保留 30 天，单批最多清理 500 条。
- 不删除待执行或执行中的任务。

`system.permission_cache_invalidate`：

- 菜单或租户套餐权限变更后，先将失效事件持久化到 `maintenance` 队列，再同步递增 Redis 权限缓存版本。
- Redis 连续三次刷新失败时，发起变更的实例立即旁路对应权限缓存，并由已持久化任务继续重试。
- 任务载荷只允许 `menu` 和 `tenant_package` 两种 scope；租户套餐失效必须携带有效租户 ID。
- 最大尝试次数为 10，任意管理后台实例均可抢占并执行，适用于多实例部署。
- 发起变更的实例在刷新失败后立即旁路对应权限缓存，不能继续信任旧缓存。
- Redis 恢复后，worker 递增共享版本号，使其他实例的旧缓存键自然失效。

## 8. 管理后台

路径：`/system/async-task`

能力：

- 查看任务健康汇总：任务总数、待执行超时、运行租约过期、失败任务和重试压力。
- 按任务类型、状态、队列和租户筛选。
- 查看执行次数、脱敏摘要、结果、最近错误和关键时间。
- 取消待执行任务。
- 人工重试失败任务。

菜单和 API 均属于平台控制面，不能只依赖前端隐藏。

健康汇总接口：

- `GET /admin/v1/async-tasks:stats`
- 默认以 5 分钟作为待执行超时阈值，也可通过 `pending_overdue_seconds` 指定。
- `pending_overdue`：`PENDING` 且 `scheduled_at` 早于阈值的任务数。
- `running_lease_expired`：`RUNNING` 且租约已过期的任务数。
- `retry_pressure`：`PENDING` 或 `RUNNING` 且执行次数已接近最大尝试次数的任务数。
- `health_status`：统一健康等级，`healthy` 表示无告警，`warning` 表示存在积压或失败任务，`critical` 表示存在租约过期或重试压力。
- `alerts`：面向后台和后续告警系统的结构化告警项，当前 code 包含 `pending_overdue`、`failed`、`running_lease_expired` 和 `retry_pressure`。
- 可按 `queue` 限定统计范围。

## 9. 后续扩展

当前首期明确不包含：

- 任意外部任务创建 API。
- Cron 表达式和周期任务定义。
- 超过 2 分钟的长任务租约续期。
- 运行中任务的强制中断。
- 独立 worker 服务和按队列水平扩缩容。
- 死信队列、任务事件通知和 Prometheus 指标。

后续顺序：

1. 增加租约心跳和长任务取消协作协议。
2. 将套餐定时发布迁移到注册 handler。
3. 接入通知、文件处理和批量导入导出任务。
4. 增加队列并发配置、执行指标和失败告警。
5. 当负载需要独立扩缩容时，将 worker 从管理后台进程拆为独立部署单元，继续复用任务表和 handler 契约。

## 10. 验收标准

- 相同幂等键重复入队只产生一个任务。
- 多 worker 不能同时获得同一有效租约。
- worker 异常后任务可在租约过期后接管。
- 失败任务按退避策略重试并在达到上限后进入失败状态。
- 非租约持有者不能完成或覆盖任务结果。
- handler panic 不会导致服务退出。
- 普通租户不能访问任务管理 API。
- 管理员可以筛选任务、取消待执行任务和重试失败任务。
- 管理员可以查看任务健康汇总，快速识别积压、失败和租约异常。
- 终态保留期清理不会删除待执行或执行中的任务。
- Redis 不可用时权限变更会生成持久化失效任务，并在恢复后由任意 worker 完成。

## 11. 真实环境验证记录

2026-07-01 在本地 MySQL 和 Redis 环境完成：

- Ent Schema 迁移成功，模拟数据校验得到 5 条任务（4 条展示任务和 1 条 worker 自动创建的每日维护任务）。
- 服务启动后，`system.task_retention_cleanup` 被 worker 抢占并在同一秒内完成，执行次数为 1。
- 平台管理员可以查询任务列表和详情。
- 待执行任务取消成功；再次取消返回 `409 ASYNC_TASK_NOT_CANCELABLE`。
- 失败任务人工重试后回到待执行状态，并在下一轮轮询中执行成功。
- 普通业务租户请求任务列表返回 `403 FORBIDDEN`。
- 服务停止时 worker、HTTP 和 gRPC 按 Kratos 生命周期顺序正常退出。
