# 平台底座生产化优化实施计划

## 1. 目标

本计划用于把当前多租户管理后台从“功能可演示”推进到“权限边界可验证、失败可恢复、生产配置可守门、质量可持续”的项目开发底座。

实施顺序遵循安全性和数据一致性优先于功能扩展的原则。业务套餐能力扩展、通用数据权限覆盖和服务拆分在本轮核心链路稳定后继续推进。

## 2. 优先级

### P0：授权闭环与租户开通一致性

- 普通租户角色的菜单按钮权限必须参与后端接口鉴权，不能只控制前端显示。
- 平台管理员继续由 Casbin 平台策略授权；普通租户角色以数据库中的用户、角色、菜单关系为权限事实源。
- 租户开通后同步授权策略失败时，必须清理策略并回滚已初始化的租户、部门、角色、用户和套餐绑定。
- 跨租户访问必须在授权层和数据层同时拒绝。

验收：

- 普通角色只能访问角色已绑定 `auth_code` 的接口。
- 删除角色按钮权限后，相同用户再次请求立即被拒绝。
- 普通租户用户不能访问平台控制面接口。
- 模拟策略同步失败后，不留下可登录的半成品租户。

### P1：缓存一致性与生产安全门禁

- 套餐变更、租户换套餐、菜单权限变更后，权限缓存必须可靠失效。
- Redis 短暂故障不能让权限撤销长期失效；失效操作需要重试和可观测记录。
- 生产镜像必须显式启用生产环境校验，禁止弱口令、开发密钥和缺失的安全中间件配置启动。
- 提供可直接校验的生产配置样例。

验收：

- 权限撤销后，缓存命中场景也不能继续放行。
- Redis 故障恢复后，待处理的缓存失效任务能够自动重试成功。
- 使用开发配置启动生产镜像时进程拒绝启动。

### P2：质量门禁与真实链路验证

- 后端覆盖授权、跨租户隔离、开通补偿和缓存失效测试。
- 前端覆盖普通租户角色登录、菜单可见性和接口拒绝行为。
- Mock 数据同时包含平台管理员、租户管理员、普通角色和跨租户验证数据。
- 根仓库提供统一的后端测试、前端类型检查和关键 E2E 执行入口。

验收：

- 后端全量测试通过。
- 前端类型检查和构建通过。
- 管理后台管理员与普通角色关键流程 E2E 通过。
- Mock 初始化可重复执行并完成内置数据校验。

### P3：底座能力扩展

- 业务套餐从菜单集合扩展为菜单、接口权限、资源额度和功能开关的版本化能力包。
- 通用数据权限从用户查询扩展到项目、审计、字典、参数等租户资源。
- 增加通知中心、文件中心、Webhook、配额计量、幂等和分布式追踪等通用底座能力。
- 达到独立部署和数据生命周期条件后，再拆分新的 Kratos 服务。

## 4. 架构约束

- 前端菜单隐藏不是安全边界，所有受保护操作必须由后端授权器判定。
- 菜单 `auth_code` 必须使用生成契约中的完整操作名，不允许使用页面路径代替接口权限。
- 普通角色权限以数据库关系为事实源，避免 Casbin 和业务表双写造成漂移；Casbin 保留平台控制面和超级管理员策略。
- 任何跨数据库与策略存储的写入都必须具备补偿、重试或持久化任务机制。
- 权限撤销优先保证正确性。缓存不可用时允许降级读取数据库，不允许继续信任无法确认版本的旧缓存。

## 5. 后续复盘要求

每完成一个优先级，必须在本文件更新状态，并记录：

- 实际变更文件和数据迁移；
- 自动化测试与真实环境验证命令；
- 未解决风险及进入下一阶段的条件；
- 对 API、数据模型、Mock 和运维配置的兼容性影响。

## 7. 未完成风险

- 权限缓存失效已接入先持久化、后刷新 Redis 的失效意图机制，可覆盖 Redis 暂时不可用和多实例重试。生产环境仍需要对持久化失败日志、连续重试失败任务和 Redis 版本刷新失败配置集中告警。
- 普通角色权限当前由数据库实时判定，正确性优先但会增加授权查询压力。完成可靠版本缓存后，应增加授权快照缓存和压测基线。
- 套餐目前仍以菜单和按钮权限为主体，接口能力包、功能开关、额度和资源授权需要按 P3 演进。
