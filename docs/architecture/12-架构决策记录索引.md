# 架构决策记录索引

日期：2026-07-10  
状态：生效  
范围：项目开发底座 P0/P1

## ADR-001：`platform/admin` 是平台管理后台基础服务

决策：`backend-service/app/platform/admin` 只承载项目开发底座管理后台基础能力，包括认证、用户、角色、菜单、租户、租户业务套餐、参数、字典、日志、会话、异步任务和项目服务配置入口。

约束：

- 具体业务生命周期不得进入 `platform/admin`。
- 业务服务需要独立边界评审。
- 平台服务可管理业务服务配置，但不实现业务服务本体。

依据：底座必须保持纯粹，避免再次退化为单业务后台。

## ADR-002：租户业务套餐优先于租户单独配置

决策：租户菜单权限采用“租户业务套餐 -> 租户绑定套餐 -> 租户内角色二次授权”的模型。

约束：

- 新租户必须先绑定一个或多个业务套餐。
- 角色授权菜单必须是租户有效菜单集合的子集。
- 租户单独菜单覆盖是后续扩展点，不作为默认开通路径。

依据：套餐可以复用同类租户授权，降低开通成本，并为版本化、回滚和缓存失效提供稳定边界。

## ADR-003：菜单权限缓存以正确性优先

决策：菜单权限缓存不能成为授权事实源。权限事实源仍是数据库关系和后端授权器，缓存只用于降低查询压力。

约束：

- 系统菜单变更、套餐发布/回滚、租户绑定套餐变更必须刷新缓存版本。
- Redis 不可用时允许降级读取数据库，不允许长期信任无法确认版本的旧缓存。
- 缓存失效意图必须先持久化为异步任务，再尝试同步刷新 Redis 版本；刷新失败时必须安全旁路。

依据：权限撤销和租户隔离的正确性优先级高于性能。

## ADR-004：前端 API 类型暂不恢复旧 `src/api/gen`

决策：当前阶段前端 API 类型按项目现有手写方式维护，不默认使用历史 proto 生成目录 `src/api/gen`。

约束：

- request/response 命名、分页结构、枚举和错误处理必须统一。
- 后端 proto 仍是服务契约事实源；前端手写类型必须跟随接口变更更新。
- 如未来恢复生成链路，必须先制定生成目录、覆盖策略和迁移计划。

依据：当前前端已经按 Vben 项目方式落地，直接恢复旧生成目录会引入双类型来源和迁移风险。

## ADR-005：测试基线先于继续扩展

决策：P0/P1 执行前先提交已补充的后端测试基线，再继续文档、隔离、缓存和权限加固。

约束：

- 测试基线提交只包含测试文件。
- 后续生产代码修复必须有对应回归测试。
- 根仓库不得混入 `.codex/.claude/.agents/.reasonix` 等无关变更。

依据：先建立可回归基线，避免后续架构和功能加固混在一个不可审查的大提交中。
