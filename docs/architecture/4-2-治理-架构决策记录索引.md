## 当前生效 ADR

### ADR-001：`platform/service` 为平台基础服务（原 `platform/admin`）

**决策：** 业务生命周期不入 `platform/service`，业务服务需独立边界评审。

**被拒绝的方案：**
- ❌ 所有业务都进 `platform/service` — 导致基础服务和业务逻辑耦合，无法独立部署
- ❌ 每个业务模块默认独立 Kratos service — 早期过度拆分，增加运维成本而无实际收益

**选择理由：** 大仓内模块化优先，既保持代码共享便利，又保留未来拆分能力。只有出现独立部署/扩缩容/数据生命周期/团队 ownership 时才拆。

---

### ADR-002：套餐优先模型

**决策：** 菜单通过 套餐→租户绑定→角色（套餐子集）二次授权，而非租户直接绑定菜单。

**被拒绝的方案：**
- ❌ 租户直接绑定菜单 — 无法支撑多租户差异化定价和批量套餐变更
- ❌ 角色直连菜单（无套餐层） — 每次新增租户需手工配置所有角色的菜单

**选择理由：** 套餐作为可版本化、可复用的能力包，是 SaaS 商业化的基础抽象。三级链路（套餐→租户→角色）既满足差异化也支持批量管理。

---

### ADR-003：缓存不可信原则

**决策：** 缓存不是授权事实来源。缓存失效意图必须先持久化再刷新 Redis。

**被拒绝的方案：**
- ❌ 缓存即事实来源（Cache-as-Source-of-Truth） — 缓存不一致时权限泄露
- ❌ 实时刷新缓存（同步写入） — 增加业务响应延迟，且刷新失败影响主流程

**选择理由：** 授权正确性不可妥协。异步刷新 + 版本号 double-check + DB 降级方案确保缓存失败不影响安全性。

---

### ADR-004：前端 API 类型手写

**决策：** 前端 API 类型手写维护，Proto 为契约唯一来源。不再使用 `src/api/gen` 自动生成。

**被拒绝的方案：**
- ❌ 继续使用 `src/api/gen` 自动生成 — 生成物与 Vben Admin 类型系统冲突，维护成本超过收益
- ❌ Proto → TypeScript 自动生成 — Buf 前端插件不够成熟，类型推导能力有限

**选择理由：** 手写类型让前端开发者明确理解 API 契约。Proto 仍是后端事实来源，前端类型的变化需要后端确认。

---

### ADR-005：测试基线策略

**决策：** 测试基线先提交再扩展。生产缺陷修复必须带回归测试。

**被拒绝的方案：**
- ❌ 先写测试再写代码（纯 TDD） — 当前阶段需求变化快，过度测试降低迭代速度
- ❌ 不做测试基线 — 质量退化风险不可接受

**选择理由：** 务实质量策略——保证已实现功能不退化，为未来扩展留出测试空间。

---

### ADR-006：大仓 + 模块化优先

**决策：** Go/Kratos 大仓模式，`app/` 下模块化。不因新增业务模块默认创建新 service。

**被拒绝的方案：**
- ❌ 微服务优先 — 早期拆分带来网络延迟、分布式事务、运维复杂度，ROI 为负
- ❌ 纯单体 — 缺乏未来拆分路径，代码边界模糊

**选择理由：** 大仓保留共享代码和统一发版便利，`app/` 目录结构保留微服务拆分能力。拆分需要满足五条件（独立部署/扩缩/API/数据/团队）。

---

### ADR-007：产品间物理隔离

**决策：** 产品 A 不能直接访问产品 B 的数据库表。跨产品数据交换走 API。

**被拒绝的方案：**
- ❌ 产品共享数据库 — 单产品故障可能拖垮其他产品，也无法独立备份和计费
- ❌ 共享 Schema + 产品字段区分 — 查询时容易遗漏过滤导致数据泄露

**选择理由：** 物理隔离是数据安全的最强保证。即使应用层漏写隔离逻辑，Schema 级别的分离也能兜底。

---

### ADR-008：统一租户底座

**决策：** 一个客户 = 一个租户，可开通多个产品线。不按产品线分拆租户。

**被拒绝的方案：**
- ❌ 每个产品线独立租户 — 同一客户在 GEO 和 CRM 中有两个租户 ID，无法统一管理用户和计费
- ❌ 全局用户池 + 产品级工作空间 — 概念复杂，实现和维护成本高

**选择理由：** "一个客户一个租户"是最自然的 B2B SaaS 模型。租户内开通多产品线，数据在产品间隔离，用户和权限统一管理。

---

### ADR-009：产品线注册制

**决策：** 新产品接入走配置注册（编码/菜单/定价/配额/表单），不改中台代码。

**被拒绝的方案：**
- ❌ 新产品接入需修改平台代码 — 每个产品上线都改中台，不可扩展
- ❌ 完全插件化 — 需要插件框架、动态加载、沙箱隔离，过度设计

**选择理由：** 注册制 = 配置驱动而非代码驱动。6 步接入流程（3 纯配置 + 3 需开发）平衡了灵活性和安全性。

## 新增 ADR 规则

- 架构决策必须在 `docs/architecture/` 下记录
- 不在产品需求或旧归档文档中散写架构决定
- 每次新增 ADR 更新本索引
- 根仓库提交不得混入 `.codex/`、`.claude/`、`.agents/`、`.reasonix/` 等工具配置变更与业务代码或架构文档无关的混合提交

### ADR 触发清单

当出现以下任一动作时，必须先起草 ADR（或在已有 ADR 下增补"递进记录"），再进入实施：

1. 新增/修改/废除核心公共包（`pkg/*` 内的独立能力，如 `auth` / `storage` / `asr`）
2. 修改分层依赖方向（`service → biz → data` 三角关系调整、跨产品服务引用）
3. 改变公共 API 契约（`/platform/v1` / `/evie/v1` / `/ai/v1` 下的面向多产品/外部的 API）
4. 引入/替换/升级核心框架或运行时（如 Kratos 版本/Ent 版本/数据库驱动/缓存后端）
5. 修改产品接入清单（`4-1` 后端 9 项/前端 10 项中的强制项）
6. 修改 Agent 决策权或协作模式（本仓内该决策本身需在 4-2 + `.agents/AGENTS.md` 双备案）
7. 修改 ADR 触发清单本身（此清单增删项）

未在以上场景的「局部实现选择」允许 Agent 在 `autonomous` 档内自主处理。

### ADR-010：Agent 决策权限分级与协作三模式

**决策：** 在 `.agents/AGENTS.md` 中正式确立 **Agent 决策权限三档分级**（`autonomous` / `requires-confirmation` / `forbidden`）与**协作三模式**（`Explore` / `Implement` / `Review`），并要求所有 AI Coding Agent（Claude Code、Codex 等）按三档与三模式门禁执行。

**被拒绝的方案：**
- ❌ 沿用「隐式三档」描述（仅在 .agents/skills/avmc-feature-delivery 等位置零散提及）—— 无法被 Agent 在决策点主动加载，出现越权时无规范依据
- ❌ 全部走「requires-confirmation」—— Agent 无法自主完成常规重构/文档/静态检查，严重低代打产品交付速度
- ❌ 「一次性全成」文档化决策不加 skill 化执行载体 —— 规范成文但 Agent 不调用，沦为存量文档

**选择理由：**
- 大仓 + Agent 协作场景下，决策权不明确会产生两类严重风险：① Agent 越权改公共契约/平台边界，人为重创难追；② Agent 对简单任务也走确认，迭代效率仅能人工。
- `requires-confirmation` 与 `forbidden` 覆盖了 8 + 7 个具体触发项（新增核心基础设施/修改租户隔离/认证授权/公共 API 契约/大规模 DB 迁移/新核心框架/平台-产品边界/跨产品公共能力/产品定位/业务规则/商业模式/产品优先级/未讨论架构/破坏性 API），是当前大仓中“容易越权但后果不迫在眉睫”的高频场景。
- 三模式门禁“未确认方案不得进入 Implement”与“Review 发现的缺陷回退 Implement”点状、不可被 Agent 跳过的阶段门，交叉了现有 skill 体系（`avmc-feature-delivery` / `avmc-cross-repo-review` / `avmc-contract-first-backend` / `agent-decision-boundary`），不需新起炉。
- 人读总纲在 `docs/architecture/0-4-架构总览-工程治理总纲.md` §五、§六；可执行载体在 `.agents/skills/agent-decision-boundary/SKILL.md`（含 `autonomous` / `requires-confirmation` / `forbidden` 触发模板与反例）。

**生效范围：** 所有进入本仓的 AI Coding Agent 与 human 协作者。

**与本仓已有体系的对齐：**
- `RULES.md` 依赖方向硬规则 → autonomous 必须遵守
- `REVIEW.md` 阻断项（`S01-S07` / `A01-A07` / `C01-C06` / `D01-D05` / `E01-E05` / `F01-F06` / `T01-T05` / `FE01-FE09` / `R01-R06`）→ required-confirmation / forbidden 都以 REVIEW 为执行载体
- `0-4 §五、§六` 总纲摘要 → 人类阅读路径
- `avmc-feature-delivery` skill → 三模式的实施体
- `agent-decision-boundary` skill → 三档的可执行载体

**状态：** 生效（2026-09 记录）。
**逆接记录：** 起始于 2026-09「工程治理总纲」立项 + `.agents/AGENTS.md` §Agent 决策权限分级 + §协作模式 双章发布。

### ADR-011：多端服务子仓库 `mobile-desktop-service` 独立 + 三栈共存

**决策：** 新增 `mobile-desktop-service` 为 Ark Tech Platform 的第三个独立子仓库，承载桌面端 + 移动端 + 小程序端。三栈（Flutter / React Native / uni-app）**不强求统一**工具链，各栈使用生态原生工具，仅在**公共契约**（proto 生成、设计令牌、CI 入口）上保持一致。

**被拒绝的方案：**
- ❌ 所有端归入 `frontend-service` — 端形态、能力、发布渠道差异巨大（Web 浏览器 vs iOS/Android/Desktop/小程序），生命周期与团队不重叠，耦合会限制选型
- ❌ 每端一个子仓（`avmc-flutter-service` / `avmc-rn-service` / `avmc-uniapp-service`）— 三个仓各需完整 .agents / docs / ci 配置，维护成本高；跨端共享（design tokens、proto 客户端）需要额外机制
- ❌ 强制三栈统一使用一套工具链（单一 pnpm 或单一 Melos）— Flutter 项目用 pnpm 管理会失去 very_good_cli 生态，uni-app 用 Melos 与 HBuilderX 冲突，逆向迁就一套工具会抹平生态优势

**选择理由：**
- **仓库结构**：`apps/`（独立产品应用）+ `packages/`（跨应用共享）+ `tooling/`（仓库级 CI / codegen / scripts），语义化命名禁止 `common/` `utils/` `helpers/` 杂物堆
- **三栈边界**：
  - Flutter 应用用 Melos 编排 + `very_good_analysis` 静态分析 + `flutter_test`；状态管理默认 `flutter_bloc`（兼容 very_good_cli），可选 Riverpod
  - React Native 用 pnpm workspaces + ESLint + `react-native-testing-library`；状态管理 `zustand`
  - uni-app 用 HBuilderX（开发）+ CLI（CI 自动化）+ ESLint；状态管理 `Pinia`（Vue 生态原生）
- **跨端共享**：`tokens.json` 作为设计令牌 SSOT，通过 `sync_design_tokens.sh` 同步到三端；`backend-service/proto/` 作为 API 契约 SSOT，通过 `gen_clients.sh` 一次生成 Dart + TypeScript 客户端
- **CI 变更驱动**：用 `dorny/paths-filter` 检测文件路径（`apps/*/lib/**` → Flutter / `apps/*/src/**` → RN / `apps/*/pages/**` → uni-app），只对受影响栈触发对应工作流
- **与 backend-service / frontend-service 边界**：
  - Web 后台功能归 `frontend-service`，不进 mobile-desktop-service
  - 任何业务 API 契约定义在 `backend-service/proto/`，所有端从这里生成客户端（不重复定义）
  - 鉴权由 `backend-service/pkg/auth` 统一管理，客户端不存凭证

**生效范围：**
- 仓库结构：`mobile-desktop-service/AGENTS.md` + `mobile-desktop-service/ARCHITECTURE.md` + `mobile-desktop-service/tool/{init_monorepo,gen_clients,sync_design_tokens,run_all_checks,upgrade_dependencies}.sh`
- Skill：`avmc-mobile-desktop-monorepo`（完整版）+ `avmc-flutter-app`（完整版，支持 bloc/riverpod 双模式）+ `avmc-react-native-app`（基础版，待实战验证）+ `avmc-uniapp-app`（基础版，待实战验证）
- 首批应用：`apps/growth_companion`（Flutter，very_good_cli 脚手架 + bloc）

**与本仓已有体系的对齐：**
- 与 ADR-010（Agent 决策权限）联动：跨端改动涉及破坏性契约 → `requires-confirmation` 档位
- 与 ADR-007（产品间物理隔离）联动：mobile-desktop-service 是「端承载层」不是「产品服务」，不重复实现业务逻辑
- 与 ADR-006（大仓 + 模块化优先）联动：多端服务采用 monorepo + 模块化，每个 `apps/<name>/` 是独立产品边界
- 4 个 skill 集成到 `.agents/skills/`，遵循 `RULES.md` 文档层级

**状态：** 生效（2026-09-21 记录，commit cdc956c + 2ed86d5）。

## Git 提交规范

| 规则 | 说明 |
|------|------|
| 子仓库先提交 | 后端代码在 `backend-service` 内提交，前端在 `frontend-service` 内提交 |
| 根仓库后提交 | 只含文档变更、子仓库指针更新、根级配置变更 |
