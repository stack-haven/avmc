# P3 通用底座能力设计

日期：2026-07-17
状态：第一批内核实施
范围：`backend-service/pkg/idempotency`、`backend-service/pkg/objectstorage`、后续 `app/platform/admin`

## 1. 目标

P3 通用底座能力用于补齐业务项目服务复用率最高的基础设施：

- 通知中心：站内信、邮件、短信、Webhook 通知的统一模板、渠道、发送记录和重试。
- 文件中心：租户文件、业务附件、导入导出文件和公开资源的统一元数据、权限、配额和对象存储接入。
- Webhook：面向外部系统的事件订阅、签名投递、重试、死信和审计。
- 幂等机制：为文件上传确认、Webhook 投递、通知发送、资源预留和外部回调提供统一幂等语义。

这些能力属于项目开发底座，不绑定具体业务域。业务模块只能通过明确的底座接口接入，不能直接依赖某个云厂商 SDK 或私有表结构。

## 2. 分层原则

### 2.1 通用内核层

当前第一批只落通用内核：

- `pkg/idempotency`：通用幂等执行器，按 `scope + key + fingerprint` 判断请求是否可重放或冲突。
- `pkg/objectstorage`：对象存储接口和 S3-compatible 实现，屏蔽 AWS S3、MinIO、Cloudflare R2、阿里云 OSS S3 协议、腾讯 COS S3 协议等差异。

该层不依赖 `platform/admin`，可以被后续业务服务复用。

### 2.2 平台服务层

后续在 `app/platform/admin` 承载管理面：

- 文件中心管理文件元数据、租户归属、业务归属、访问策略、上传凭证、下载凭证、删除和审计。
- 通知中心管理模板、渠道、发送任务、发送记录、失败重试和渠道配置。
- Webhook 管理事件类型、订阅端点、签名密钥、投递任务、投递记录和死信重放。
- 幂等记录持久化应进入平台服务数据库，提供可清理、可审计、可按租户隔离的记录。

### 2.3 业务模块层

业务模块只使用底座能力：

- 文件上传：申请上传凭证 -> 客户端直传对象存储 -> 确认文件 -> 绑定业务资源。
- 通知发送：提交通知意图和模板变量，不直接调用邮件、短信或 Webhook SDK。
- Webhook 事件：发布领域事件，不直接投递 HTTP 请求。
- 幂等：所有外部写入接口、回调接口和异步投递使用业务幂等键。

## 3. 文件中心与 S3 兼容策略

文件中心底层统一依赖 `ObjectStorageClient`，当前对象存储内核支持：

- `PutObject`：服务端上传对象。
- `DeleteObject`：删除对象。
- `PresignPutObject`：生成客户端直传 URL。
- `PresignGetObject`：生成临时下载 URL。
- `PublicURL`：生成公开访问 URL。

S3-compatible 配置应包含：

- `endpoint`：存储服务地址，例如 AWS S3、MinIO、R2、OSS/COS S3 endpoint。
- `region`：签名 region，R2 或 MinIO 可使用 `auto` 或 `us-east-1`。
- `access_key` / `secret_key` / `session_token`。
- `force_path_style`：MinIO 和多数私有化部署建议开启。
- `public_base_url`：CDN 或公开下载域名，可与内部上传 endpoint 分离。
- `default_bucket`：默认桶，业务仍可按租户或模块拆 bucket。

文件中心后续表结构建议：

- `file_objects`：文件元数据、租户、业务类型、业务 ID、bucket、object key、大小、hash、content type、状态、可见性。
- `file_upload_sessions`：上传会话、预签名凭证、过期时间、幂等键、确认状态。
- `file_access_logs`：下载、预览、删除等访问审计。

## 4. 通知中心策略

通知中心不直接等同短信配置。建议拆分：

- 通知模板：模板编码、标题、内容、变量 schema、语言。
- 通知渠道：站内信、邮件、短信、Webhook。
- 通知任务：接收人、渠道、模板变量、优先级、计划发送时间。
- 通知记录：发送状态、渠道响应、失败原因、重试次数。

发送必须异步化，复用 `AsyncTask` 作为任务执行底座。每次发送使用幂等键，避免重试导致重复通知。

## 5. Webhook 策略

Webhook 是事件中心的外部投递面，不是任意 HTTP 调用工具。必须满足：

- 事件类型白名单。
- 订阅端点归属租户。
- 每个订阅独立签名密钥。
- 投递请求携带事件 ID、时间戳、签名和重试次数。
- 2xx 视为成功；非 2xx 或网络错误进入指数退避重试。
- 达到最大重试次数进入死信，支持人工重放。

Webhook 投递记录需要持久化，并使用 `scope=tenant:<id>:webhook:<subscription_id>` 与事件 ID 作为幂等键。

## 6. 幂等策略

通用幂等由三个字段决定：

- `scope`：隔离范围，例如 `tenant:100:file`、`tenant:100:webhook:9`、`platform:quota`。
- `key`：业务幂等键，例如上传会话 ID、外部回调 ID、事件 ID。
- `fingerprint`：请求语义摘要，同一个 key 被不同请求体复用时必须返回冲突。

处理规则：

1. 第一次请求执行真实处理并保存结果。
2. 相同 `scope + key + fingerprint` 再次请求直接回放第一次结果。
3. 相同 `scope + key` 但 `fingerprint` 不同，返回幂等冲突。
4. 处理函数失败时不保存成功结果，允许重试。
5. 持久化实现必须支持过期清理，避免幂等记录无限增长。

## 7. 实施顺序

1. 第一批：通用幂等内核、S3-compatible 对象存储内核、架构文档。
2. 第二批：文件中心 proto、Ent schema、上传会话、文件元数据、S3 预签名 API、mock 数据和前端页面。
3. 第三批：通知中心 proto、模板/渠道/记录、异步发送任务、站内信 MVP。
4. 第四批：Webhook 事件订阅、投递任务、签名验证、重试和死信。
5. 第五批：所有 P3 能力接入资源额度、操作日志、租户套餐能力和前端权限菜单。
