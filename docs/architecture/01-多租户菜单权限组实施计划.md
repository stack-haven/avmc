# 多租户业务套餐与菜单权限实施计划

日期：2026-06-23  
状态：MVP 已完成，进入联调与后续迭代  
范围：`backend-service/app/platform/admin`、`frontend-service/apps/web-antd-admin`、底座管理后台权限体系

## 1. 背景

项目开发底座需要支持多租户中台管理。平台侧需要统一管理租户、全局菜单池、租户可用菜单范围和租户内角色权限。为了避免每个租户重复勾选菜单，租户菜单授权采用“业务套餐优先”的模型。

产品侧统一使用“租户业务套餐”命名。工程侧暂复用 `MenuPermissionGroup`、`TenantPermissionGroup` 现有契约和数据表，避免在 MVP 阶段重复建模。后续如进入计费、服务市场或套餐版本管理，再评估是否拆出独立 `TenantPackage` 聚合。

本能力属于底座管理后台基础能力，默认落点为：

- 后端：`backend-service/app/platform/admin`
- 前端：`frontend-service/apps/web-antd-admin`

本能力不属于应用版本管理中心（AVMC）业务服务。

## 2. 设计目标

- 平台维护全局菜单池。
- 平台维护租户业务套餐，用于表达一组可复用的菜单和按钮权限。
- 租户通过绑定一个或多个业务套餐快速开通功能。
- 租户管理员只能在租户已获得的菜单范围内给角色二次分配权限。
- 登录菜单和权限码由后端计算，不能只依赖前端隐藏。
- 后续可扩展套餐、项目服务权限组、租户单独覆盖配置和操作审计。

## 3. 权限模型

有效权限按以下顺序收敛：

```text
平台菜单池
  -> 租户业务套餐
  -> 租户绑定业务套餐
  -> 租户内角色二次分配
  -> 用户最终菜单/权限
```

用户最终有效菜单和权限码：

```text
用户有效菜单/权限 = 全局菜单启用
  ∩ 租户绑定业务套餐包含的菜单
  ∩ 用户角色已授权菜单
  ∩ 租户/用户/角色启用状态
```

租户级别单独加减菜单作为后续扩展点，不进入 MVP 默认实现。

## 4. 核心对象

### 4.1 平台菜单池

复用当前 `Menu` 模型，继续由平台管理员维护。

菜单池包含：

- 目录
- 菜单
- 按钮
- 内嵌页面
- 外链
- 权限码
- 路由与组件信息

### 4.2 租户业务套餐

`MenuPermissionGroup` 用于复用一组菜单授权。产品层称为“租户业务套餐”。

建议字段：

- `id`
- `name`
- `code`
- `status`
- `description`
- `remark`
- `is_system`
- `sort`
- `menu_ids`
- `created_at`
- `updated_at`

约束：

- `code` 全局唯一。
- `name` 全局唯一。
- 系统权限组可以修改菜单，但默认不允许删除。
- 禁用权限组后，绑定该权限组的租户不再获得该组菜单。

### 4.3 租户业务套餐绑定

`TenantPermissionGroupBinding` 表达租户绑定了哪些业务套餐。

建议字段：

- `tenant_id`
- `group_id`
- `enabled`
- `bound_by`
- `bound_at`
- `created_at`
- `updated_at`

约束：

- 一个租户允许绑定多个业务套餐。
- 一个租户和一个业务套餐只能存在一条有效绑定。
- 绑定禁用业务套餐不应产生有效菜单。

### 4.4 租户内角色权限

复用当前 `Role.menu_ids`。

新增规则：

- 创建或更新角色时，`menu_ids` 必须是当前租户有效菜单集合的子集。
- 平台超级管理员需要管理某个租户角色时，也必须显式进入目标租户上下文。
- 角色不能通过 API 绕过租户权限组直接绑定全局菜单。

## 5. MVP 范围

### 5.1 后端

- 新增租户菜单权限组契约。
- 新增租户绑定权限组契约。
- 新增平台租户管理契约。
- 新增权限组与菜单、租户与权限组的数据模型。
- 角色创建和更新时校验菜单必须来自租户有效权限组。
- 登录菜单和权限码叠加租户权限组过滤。
- 租户权限组变更后立即影响登录菜单、权限码和角色授权校验。

### 5.2 前端

- 新增“租户业务套餐”页面。
- 在“租户管理”创建和编辑流程中支持绑定业务套餐。
- 角色权限树只展示当前租户有效菜单。
- 权限组修改时提示会影响已绑定租户。

### 5.3 文档

- 本文档作为实施依据。
- 后续每次权限体系调整，应更新本文档或新增后续 ADR。

## 6. 非目标

MVP 暂不实现：

- 租户单独菜单覆盖配置。
- 套餐计费。
- 项目服务市场。
- 复杂数据权限表达式。
- API 级独立权限资源表。
- 多租户独立库或独立 schema。

## 8. 数据模型计划

新增 Ent schema：

- `MenuPermissionGroup`
- `TenantPermissionGroup`
- `Tenant`

关系：

```text
MenuPermissionGroup * -> * Menu
Tenant * -> * MenuPermissionGroup
Role * -> * Menu
User * -> * Role
```

`TenantPermissionGroup` 需要绑定真实租户，后续租户删除策略、租户初始化流程和租户数据隔离策略需要基于 `Tenant` schema 继续扩展。

## 10. 验收标准

- 平台管理员可以创建租户业务套餐并绑定菜单。
- 平台管理员可以维护租户，并把一个或多个业务套餐绑定给租户。
- 租户管理员创建角色时，只能选择租户有效菜单。
- 如果角色提交了租户未授权菜单，后端返回权限错误。
- 用户登录后菜单只包含角色菜单和租户权限组菜单的交集。
- 用户权限码只包含最终有效按钮或权限码。
- 禁用权限组后，绑定租户不再获得该组菜单。
- 删除权限组前，如果仍有租户绑定，应被阻止或要求先解绑。

## 12. 当前行为

- 租户没有绑定任何启用的菜单权限组时，租户有效菜单为空。
- 权限组禁用后，绑定该权限组的租户不再获得该组菜单。
- 角色不能保存租户未获得的菜单 ID。
- 登录菜单只返回“角色菜单”和“租户有效菜单”的交集，并自动补齐可见菜单父级。
- 当前租户有效菜单接口可供前端角色授权树使用，避免前端自行拼接租户权限。
- 租户创建和编辑时需要至少选择一个租户业务套餐，避免新租户创建后没有任何菜单权限。
- 租户有效菜单 ID 走版本化缓存；缓存失效通过版本递增实现，不依赖批量删除历史 key。

### 13.2 联调测试链路

建议使用独立测试库验证，不直接污染开发主库：

- MySQL：`platform_system_e2e`
- Redis：独立 Redis DB 或清晰的测试 key 前缀
- 后台服务端口：避免占用默认端口，可使用 `18080/19090`

测试步骤：

1. 创建测试库。
2. 使用 `cmd/migrate` 对测试库执行 Ent schema 迁移。
3. 写入测试租户、全局菜单池、菜单权限组、租户权限组绑定、测试用户、测试角色。
4. 执行 `cmd/policy` 同步测试用户的 `super_admin` Casbin 策略。
5. 启动 `app/platform/admin` 后台服务。
6. 使用测试用户登录并获取 Bearer Token。
7. 验证以下 HTTP 行为：
   - `GET /admin/v1/tenants/{id}` 返回测试租户。
   - `GET /admin/v1/current-tenant/effective-menus` 只返回租户权限组内菜单。
   - `POST /admin/v1/roles` 提交租户未授权菜单时必须失败。
   - `GET /admin/v1/auth/menus` 返回“租户权限组 ∩ 角色菜单”的交集。
   - `GET /admin/v1/auth/codes` 只返回最终有效菜单或按钮权限码。

## 14. 前端接口规则

`apps/web-antd-admin/src/api/gen` 是历史上通过 proto 给前端生成接口和字段的旧方案，当前底座管理后台不再默认使用它。

新的前端开发规则：

- 不恢复 `apps/web-antd-admin/src/api/gen` 作为默认依赖。
- 不把 proto 生成前端接口作为当前后台页面开发前置条件。
- 每个后台模块在 `src/api/system/*.ts` 中维护轻量 API wrapper 和当前页面所需 TypeScript interface。
- 公共枚举和通用响应类型放在 `src/api/type/index.ts`，使用本地常量表达，例如 `STATUS_ENABLED`、`STATUS_DISABLED`。
- 页面局部字段、筛选项、表单 schema 继续放在 `src/views/system/<module>/data.ts`。
- 后端契约仍以 proto 为准；前端类型以接口实际响应字段和页面需求收敛，不追求与 proto 生成物一一绑定。

## 15. 生成限制

标准命令：

```bash
make proto
```

会调用 Buf 远程插件。此前执行被安全策略拒绝，因为该操作会把 proto 契约发送到 Buf 远程插件基础设施。为避免外发仓库契约，本次使用本地模板生成新增 API：

```bash
cd backend-service/proto
buf generate --template buf.local.gen.yaml
```

后续如果需要恢复完整 OpenAPI 或远程插件生成，需要由项目负责人明确授权。
