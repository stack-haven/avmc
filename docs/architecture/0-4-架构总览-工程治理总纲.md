## 一、术语与平台定位

**Ark Tech Platform** 是面向多产品 SaaS 的技术平台，承载多个 Ark Product Services。平台包含三层：

| 层 | 含义 | 当前代表 |
|---|---|---|
| 技术中台（Platform Foundation） | 多租户、认证、套餐、配额、审计、文件、通知、任务、参数配置 | `backend-service/app/platform/service` |
| 业务中台（Business Platform） | 产品注册、订阅计费、客户运营、渠道佣金 | 设计中，详见 `2-业务中台/*` |
| 产品服务（Product Services） | 面向终端业务场景的具体产品 | Evie ASR（active）、GEO Engine（planning）、AI Agent Management（planning）、App Version Management（historical） |

术语约定：

- 「**Platform**」「**平台**」在本文中默认指**技术中台**，对应 `backend-service/app/platform/service`，不再指代整个 Ark Tech Platform。
- 「**Ark Tech Platform**」「**平台**」整体」指技术中台 + 业务中台 + 产品服务的总和。
- 「**Evie ASR**」是当前唯一处于 **active** 状态的产品服务；其余产品服务在完成 `docs/services` 定义、4-1 接入清单评审与子仓库提交后，方可进入 active。

平台同时需要满足：多产品共存、产品独立演进、公共能力复用、租户数据隔离、业务模块可扩展、AI 能力可接入、开源开发者可理解/使用/贡献。

## 二、设计原则

| # | 原则 | 实施细则 | 对应文档 |
|:--:|---|---|---|
| 一 | **产品优先，能力跟随验证** | 不为追求技术完整性而提前建设无产品依赖的通用能力；底座能力只在被 ≥1 个产品实际依赖且完成验证后才会纳入。路线图是规划输入，不是建设指令。 | `4-3-治理-能力路线图.md` |
| 二 | **业务边界优先，技术工具复用** | 业务领域、产品服务、服务边界之间优先互斥与隔离，禁止通过复制已有服务代码绕过边界评估；技术工具（公共包、组件、SKILL）优先复用，禁止在各业务模块内散落重复实现。 | `0-3 §5 拆分条件`、`4-2 ADR-006/007`、`RULES.md` §公共函数复用规则 |
| 三 | **业务独立于技术实现** | 业务规则不直接依赖数据库、HTTP 框架、AI 模型、外部服务；技术实现可替换，业务行为稳定。分层依赖方向：`service → biz → data`，`biz` 不 import `ent/gen`、不直接操作 Ent Client。 | `RULES.md` §依赖方向硬规则、`4-1` §后端分层编码规范 |
| 四 | **设计面向变化** | 每次架构设计必须明确：当前解决的问题、未来变化点、稳定接口、可替换实现、不值得引入的复杂度。重大决策必须以 ADR 形式记录「被拒绝方案」。 | `4-2-治理-架构决策记录索引.md` |
| 五 | **AI 生成代码必须接受工程约束** | Coding Agent 可提高开发速度，但不得绕过架构设计、测试、权限、数据隔离与文档门禁。所有 Agent 动作落入三档决策权限之一。 | `.agents/AGENTS.md` §Agent 决策权限分级、`REVIEW.md`、`.agents/skills/agent-decision-boundary` |

## 三、大仓核心目标

大仓不是把所有代码塞到一个目录，而是建立统一的工程治理边界。当前大仓分为三个 Git 仓库（根仓库 + `backend-service` + `frontend-service` 子模块），统一以下目标：

| 目标 | 当前落地 | 待补/缺口 |
|---|---|---|
| 统一依赖管理 | `go.work` + `go.mod/sum` + pnpm workspace | — |
| 统一代码规范 | `.golangci.yml`、gofmt、ESLint、Stylelint | — |
| 统一测试与构建 | `Makefile`（后端）、Turbo（前端）、vitest | 覆盖率门禁未在 CI 中强制（见 §七） |
| 统一 CI/CD | `backend-service/.github/workflows/backend-ci.yml`（已修路径）、`frontend-service/.github/workflows/*` | 根仓库无集中 CI；覆盖率门禁未接入 |
| 统一公共库 | `backend-service/pkg/*`、`frontend-service/packages/*` | — |
| 独立服务发布 | `app/*/Dockerfile`、`deploy/` | — |
| 服务间依赖可追踪 | 无专门机制 | 🟡 计划接入 `depguard` 或自定义 import lint |
| 不同产品独立演进 | 三仓库（根 + 2 子仓库）+ 模块化服务边界 | — |

## 五、Agent 决策权限分级（摘要）

> 完整可执行版本见 `.agents/AGENTS.md` §Agent 决策权限分级，以及 `.agents/skills/agent-decision-boundary/SKILL.md`。

| 档位 | 含义 | 典型动作 |
|:--:|---|---|
| autonomous | Agent 可独立完成 | 已确认方案的具体实现、单元测试、常规重构、文档更新、静态检查、常规错误修复 |
| requires-confirmation | 必须取得用户/架构师确认 | 新增核心基础设施、修改租户隔离模型、修改认证授权架构、改变公共 API 契约、大规模数据库迁移、引入新核心框架、修改 Platform-Product 边界、可能影响多产品的公共能力 |
| forbidden | Agent 不得自行决定 | 产品核心定位、业务规则、商业模式、产品优先级、未经讨论的架构方向、破坏性 API 变更、跨租户/跨产品数据可见性策略 |

每条 requires-confirmation 与 forbidden 的触发项、确认对象与反例见 `agent-decision-boundary` skill。

## 六、协作模式

| 模式 | 目标 | 是否允许改代码 | 默认 skill |
|---|---|:--:|---|
| Explore 模式 | 现状发现、风险评估、影响矩阵、方案草拟 | ❌ 仅只读 | `avmc-feature-delivery`（分析侧）、`avmc-contract-first-backend`（调研侧） |
| Implement 模式 | 在已确认方案上完成编码、测试、文档、验证 | ✅ | `avmc-feature-delivery`、`avmc-contract-first-backend`、`avmc-backend-crud`、`avmc-frontend-page`、`avmc-submodule-sync` |
| Review 模式 | 功能完成后做架构/安全/测试/性能/可维护性/文档审查 | ⚠️ 仅修复审查发现 | `avmc-cross-repo-review`、`code-review-checklist`、`go-testing-code-review` |

**模式门禁**：

- 未完成 Explore 阶段并获得用户确认，不得进入 Implement。
- Implement 完成 + 自动化验证（`make check` / `buf breaking` / `pnpm typecheck & build`）通过 → `[~]`；人工功能验证 + 文档同步完成后 → `[x]`，再进入 Review。
- Review 阶段发现的缺陷一律回退到 Implement 修复，不得在 Review 模式直接改业务代码。
