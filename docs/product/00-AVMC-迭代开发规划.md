# 应用版本管理中心服务迭代开发规划

版本：v1.0  
日期：2026-06-03  
依据：`docs/archive/product-202501` 历史文档、`docs/architecture` 架构决策、`docs/vibe-coding` 规范、`.codex` 项目规则、当前前后端代码结构

## 1. 文档定位

本文档用于指导应用版本管理中心（AVMC）服务后续迭代开发。它不是一次性排期表，而是把该服务的产品能力按依赖顺序拆成可持续推进的迭代路线。

后续每个功能进入开发前，应基于本文档拆成更小的任务卡，并补充具体 API、数据模型、页面原型和验收用例。

## 2. 迭代原则

- 先打通项目、权限、版本、Release 主链路，再扩展下载页、反馈、协议、推送和 AI。
- 每个迭代都要保证前后端主路径可运行，不做只存在于文档里的功能。
- 后端以 `backend-service/proto` 为契约源头，按 `service -> biz/usecase -> data/repo -> ent schema` 实现。
- 后端当前采用“大仓 + 模块化服务边界优先”策略，`backend-service/app/platform/admin` 升级为底座管理后台基础服务。
- AVMC 版本、Release、灰度、下载页、反馈、协议、推送等业务能力不再继续落入 `backend-service/app/platform/admin`。
- Release 管理后台和客户端版本检查 API 的服务边界需要在 AVMC 业务服务落点确认后再推进。
- `backend-service/app/version/service` 当前冻结，不作为迭代 1/2 新增业务落点。
- 不因为新增业务模块就默认创建新的 Kratos service；只有出现独立部署、独立扩缩容、独立公共 API 或清晰业务域边界时，才考虑拆成独立服务。
- 前端以 `frontend-service/apps/admin-antd-avmc` 为主应用，按 `Page + useVbenVxeGrid + useVbenDrawer + useVbenForm` 实现管理页。
- 生成代码必须由源文件生成，不手工修改 `backend-service/api`、`internal/data/ent/gen` 等生成目录。
- 新增可见文案同时补中文和英文 locale key。

## 3. 迭代 0：文档和工程基线

目标：统一项目事实来源，避免后续开发被旧文档中的目录和技术栈误导。

范围：

- 确认 `.codex`、`docs/architecture`、`docs/services`、`docs/product`、`docs/vibe-coding` 的主次关系。
- 明确当前技术栈：Go + go-kratos + Protobuf + Ent + Wire，Vue 3 + Vben Admin + Ant Design Vue。
- 明确主开发目标：`backend-service/app/platform/admin` 作为底座管理后台基础服务，`backend-service/app/ai/service` 作为底座 AI/chat 能力服务，`frontend-service/apps/admin-antd-avmc` 暂作为底座管理后台前端；`backend-service/app/version/service` 当前冻结，只作为复审候选。
- 旧产品文档归档到 `docs/archive/product-202501`，只作为历史资料。

完成标准：

- AVMC 服务产品需求总览和迭代开发规划已建立。
- Codex 代理能通过 `.codex` 文档判断默认开发路径。
- README 和 Vibe Coding 文档不再误导到旧目录。

## 4. 迭代 1：基础权限与项目管理

目标：建立多项目管理的基础边界，为版本、Release、下载页等模块提供项目归属。

当前进展：

- 项目管理后端 MVP 已完成：proto、Ent schema、repo、usecase、service、HTTP/gRPC 注册、项目成员关系基础。
- 项目管理前端基础页面已完成：列表、筛选、创建/编辑 drawer、状态切换、API wrapper、`zh-CN/en-US` 文案。
- 项目权限配置入口、项目级成员角色和操作日志仍待继续补充。

后端任务：

- 梳理现有用户、角色、菜单、部门 API。
- 补齐项目管理 API 契约。
- 在 `backend-service/app/platform/admin` 内建立项目数据模型和项目成员/权限关系。
- 增加项目状态控制。
- 增加关键操作日志能力的基础结构。

前端任务：

- 完善系统管理下用户、角色、菜单、部门页面。
- 新增项目管理页面：列表、筛选、创建/编辑、状态切换、权限配置。
- 项目状态使用 `CellTag` 或 `CellSwitch` 风格。
- 所有操作补 i18n 文案。

验收标准：

- 管理员可以创建项目、编辑项目、禁用项目。
- 项目名称唯一。
- 项目权限配置能保存并影响后续项目数据访问。
- 无权限用户不能访问非授权项目数据。

## 5. 迭代 2：版本管理 MVP

目标：建立项目下版本资料、更新包和回滚的基础能力。

后端任务：

- 定义版本管理 Protobuf 契约。
- 在新的 AVMC 业务服务边界内建立版本 Ent schema。
- 实现版本创建、编辑、详情、列表、删除、状态变更。
- 实现文件上传后的下载地址、文件大小、校验值记录。
- 实现基础回滚记录。

前端任务：

- 新增版本管理页面。
- 支持项目筛选、版本号筛选、状态筛选、创建时间筛选。
- 新增版本创建/编辑 drawer。
- 支持更新包上传字段和更新说明。
- 增加版本详情和回滚确认。

验收标准：

- 管理员可以为项目创建版本。
- 版本号格式和唯一性可校验。
- 文件信息能保存并展示。
- 回滚需要确认并记录。

## 6. 迭代 3：Release 发布与客户端版本检查

目标：把“版本资料”和“发布行为”拆开，打通客户端版本检查主链路。

后端任务：

- 定义 Release Protobuf 契约。
- 建立 Release 数据模型。
- Release 管理后台契约和数据模型在新的 AVMC 业务服务边界内实现。
- 在迭代 3 开始前确认客户端版本检查 API 是否需要升级 `backend-service/app/version/service` 为独立服务，或进入新的 AVMC 业务服务。
- 支持草稿、待发布、已发布、已撤回状态。
- 支持灰度发布和全量发布类型。
- 实现客户端版本检查 API。
- 返回更新类型、强制更新标记、下载地址、更新说明、协议提示。

前端任务：

- 新增 Release 管理页面。
- 支持基于版本创建 Release。
- 支持发布、撤回、删除、查看统计。
- Release 发布和撤回必须二次确认。

验收标准：

- 可以基于版本创建 Release 草稿。
- 已发布 Release 能被版本检查 API 命中。
- 撤回后客户端不再收到该 Release。
- 强制更新和可选更新返回结果清晰。

## 7. 迭代 4：灰度发布与发布统计

目标：降低发布风险，支持分阶段扩大更新范围。

后端任务：

- 建立灰度策略模型。
- 支持百分比、用户 ID、设备标签、地区等基础条件。
- 版本检查 API 接入灰度策略判断。
- 统计覆盖用户、成功、失败、取消和成功率。

前端任务：

- 新增灰度策略配置界面。
- 在 Release 页面展示灰度状态和指标。
- 支持调整灰度比例。
- 支持查看灰度发布效果。

验收标准：

- 灰度外用户不会收到灰度 Release。
- 调整灰度比例后新请求按新策略生效。
- 管理员可以基于统计结果决定是否全量发布。

## 8. 迭代 5：下载页配置

目标：提供面向用户的项目下载页，让运营可以配置内容和推广信息。

后端任务：

- 定义下载页配置 API。
- 建立下载页模板、内容、发布状态模型。
- 支持草稿、预览、发布。
- 提供公开下载页数据接口。

前端任务：

- 新增下载页配置列表。
- 新增模板选择、内容编辑、预览、发布流程。
- 下载页编辑页应保持后台工具型布局，避免营销式管理界面。

验收标准：

- 运营可以创建下载页草稿。
- 预览和发布结果一致。
- 发布后公开页面能获取项目、版本和下载链接信息。

## 9. 迭代 6：反馈、协议、推送

目标：补齐运营闭环和合规能力。

用户反馈：

- 支持反馈列表、详情、状态处理、附件、类型筛选。
- 支持反馈统计和导出。

协议管理：

- 支持隐私协议、服务条款、免责声明。
- 支持版本历史、多语言、生效状态。
- 客户端可获取当前生效协议。

推送通知：

- 支持创建推送任务。
- 支持按项目、分组、Release 或灰度用户选择推送范围。
- 记录发送状态和统计。

验收标准：

- 反馈可提交、查看、处理。
- 协议新版本发布后客户端能感知。
- 推送任务有可追踪的发送记录。

## 10. 迭代 7：监控、审计与多项目看板

目标：提升管理效率和可运维性。

范围：

- 多项目统一概览。
- 版本发布成功率、失败率、取消率统计。
- 用户反馈趋势。
- 操作日志与审计。
- 关键异常告警。

验收标准：

- 管理员可以看到跨项目关键指标。
- 关键发布操作可追溯。
- 异常发布状态能被及时发现。

## 11. 迭代 8：AI 与高级扩展

目标：在主业务链路稳定后，引入智能化能力。

候选能力：

- 用户反馈自动分类和摘要。
- 发布风险提示。
- 灰度扩量建议。
- 异常趋势分析。
- 智能生成 Release notes。

约束：

- AI 能力只作为辅助建议，不直接替代管理员发布决策。
- AI 输出必须可追溯、可人工确认。
- 不影响现有版本发布主链路稳定性。

## 12. 每次迭代的开发流程

1. 明确需求范围和不做范围。
2. 确认后端 API 契约和数据模型。
3. 确认前端页面结构和交互流程。
4. 后端先改 `backend-service/proto`，再生成代码，再实现 `service -> biz/usecase -> data/repo -> ent schema`。
5. 前端按 `views -> data.ts -> modules/form.vue -> api -> locales` 实现。
6. 补充测试或手工验收步骤。
7. 运行最近服务或应用的检查命令。
8. 更新相关文档。

## 13. 子仓库提交规则

`backend-service` 和 `frontend-service` 是独立子仓库。后续产品迭代涉及后端或后台代码变更时，需要分别维护子仓库提交，再回到根仓库更新子仓库指针。

规则：

- 后端代码变更在 `backend-service` 内提交。
- 前端后台代码变更在 `frontend-service` 内提交。
- 根仓库只提交文档变更、子仓库指针更新和根级配置变更。
- 不要只在根仓库提交而忽略子仓库内部提交。
- 查看状态时需要分别执行：
  - 根仓库：`git status`
  - 后端子仓库：`cd backend-service && git status`
  - 前端子仓库：`cd frontend-service && git status`

推荐提交顺序：

1. 在 `backend-service` 或 `frontend-service` 内完成代码提交。
2. 回到根仓库确认对应子仓库指针变化。
3. 在根仓库提交子仓库指针更新和相关文档。

## 14. 测试与验收要求

后端：

- 核心 usecase 应有单元测试。
- repository 涉及数据库时至少覆盖关键成功路径和失败路径。
- API 列表接口应覆盖分页、筛选、排序。
- 权限和项目隔离必须有验收用例。

前端：

- CRUD 页面验证列表、筛选、创建、编辑、删除、状态切换。
- 确认可见文案存在 i18n key。
- 验证 drawer/modal 不溢出，按钮文案不遮挡。
- 验证无数据、加载中、错误提示。

手工验收：

- 每个模块至少保留一组完整操作路径。
- 发布、撤回、删除、回滚、推送等高风险动作必须验证二次确认。

## 15. 风险与应对

- 数据一致性风险：项目、版本、Release、灰度策略必须明确关联关系。
- 权限风险：所有项目级数据都要校验项目权限。
- 发布风险：灰度、撤回、回滚必须有确认和记录。
- 性能风险：列表接口必须分页，统计接口避免一次性加载全部数据。
- 合规风险：协议版本和用户同意状态需要可追溯。
- 文档漂移风险：实现变更后同步更新本规划或对应模块文档。

## 16. 当前建议优先级

建议近期优先推进：

1. 迭代 1：基础权限与项目管理。
2. 迭代 2：版本管理 MVP。
3. 迭代 3：Release 发布与客户端版本检查。

这三步完成后，应用版本管理中心服务才具备最小可用的版本发布主链路。
