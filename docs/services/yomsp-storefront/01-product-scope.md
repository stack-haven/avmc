## 1. 品牌说明

- **YOMSP** 暂作为业务及独立站宣传使用的品牌名称。
- 业务未成熟阶段**不要求**立即申请商标，但**上线前必须**完成基础品牌名称、域名、社媒账号和明显商标冲突检查。
- "暂不申请商标" ≠ "不需要冲突检查"。这两件事必须分开对待。

## 2. 真实性原则（不可协商）

凡未由用户或真实后端提供的数据，**一律不得伪装成真实业务数据**，包括：

- 商品价格、库存、可售状态、销量；
- 评价、评分、用户数量、客户案例；
- 认证、奖项、合作关系、专家背书；
- 公司地址、联系方式、配送时效、退换货与保修条款；
- "俄罗斯本地仓""当天发货""免费配送""俄罗斯第一"等无法证实的表述。

**规则**：样例数据必须清楚标记为 Demo / 示例数据，并与生产数据隔离（实现见 [06](06-api-and-mock.md) §5）。

## 3. 业务定位

YOMSP 是面向俄罗斯市场的爬宠用品品牌/独立站，聚焦爬宠饲养环境与相关产品，面向新手饲养者和有经验的爬宠爱好者。站点同时承担：

- 品牌展示；
- 专业产品说明与可核验参数；
- 标准产品销售（第一版仅演示购物车）；
- 标准模块化环境组合（设计器 2D 预览）；
- 专业内容获客（SEO / GEO）。

### 3.1 能力假设边界

- 项目早期以**供应商现有标准商品 + 人工选品**为主。
- **不得假设**已拥有：自有工厂、独立生产线、任意尺寸定制能力、完整俄罗斯本地履约体系。
- 朋友现有平台销售与仓储能力可作为后续调研线索，**在书面确认前不得**在站点上承诺相关库存、仓储、发货时效或履约能力。

## 4. 主要用户

| 用户 | 关注点 | 站点应对 |
|---|---|---|
| 新手用户 | 不知道为特定爬宠选什么尺寸/结构/底材/躲避/攀爬/照明 | 循序渐进的指导；设计器分步流程 |
| 资深爱好者 | 尺寸、材料、通风、结构、兼容性、SKU、参数对比 | 结构化参数表、筛选、商品详情规格 |
| 组合方案用户 | 基于标准模块搭配环境、查看布局与清单 | 环境方案页 + 设计器 + 人工确认入口 |
| 内容搜索用户 | 从俄语搜索引擎 / 生成式 AI 回答进入专业指南 | SSR 指南页、可引用结构、结构化数据 |

## 5. 价值主张

1. 专业且**可核验**的产品参数；
2. 帮用户理解**选择逻辑**的环境指南（不只是陈列商品）；
3. **标准模块化组合**，而非虚假承诺的无限定制；
4. 清楚区分「可直接购买商品 / 组合建议 / 需人工确认的特殊需求」；
5. 俄语优先、卢布价格、公制单位、清晰的购买与配送信息（仅在真实确认后展示）。

## 6. 第一版商业边界

### 6.1 第一版包含

- 品牌首页、商品目录、分类、商品详情；
- 环境方案列表与详情；
- 标准模块环境设计器（2D / 平面布局或示意图）；
- 前端演示购物车；
- 指南 / 文章内容；
- 首页内容运营原型；
- SEO 技术基础；
- 移动端 + 桌面端适配。

### 6.2 第一版不包含（除非另行批准）

- 真实支付、真实订单履约；
- 任意三维建模或复杂 3D 渲染；
- 用户随意输入任意尺寸后自动承诺生产；
- 未验证的商品兼容性自动推荐；
- 复杂个性化账户体系；
- 用户评论、评分、销量等未经真实数据支持的社会证明；
- 未确认的物流、税务、退款、支付渠道承诺;
- 生产级拖拽页面装修器；
- 以 AI 生成内容替代商品事实核验。

> 第一版中的「购物车」「设计器」「首页运营」全部是**前端演示 / 本地预览**形态，必须在 UI 上明确标注。

## 7. 对 Coding Agent 的最高优先级指令

1. **先检查，后编码**：读仓库目录、README、package.json、锁文件、Nuxt/Vue/Tailwind 配置、测试、CI、环境变量样例、API 契约和现有组件；先输出审查报告与实施计划。
2. **技术基线**：Nuxt + Vue 3 + TypeScript + Tailwind CSS；业务后端复用现有 Go API；管理中台复用现有 Vben Admin。不得未经批准替换为 React/Next.js，不得新建重复业务后端。
3. **SSR 是默认要求**：公开页必须 SSR 或预渲染，禁止 `ssr: false` 的纯 SPA 站点。
4. **先建立系统边界**：Nuxt 不直连数据库；商品/SKU/价格/库存/可售/兼容规则/订单/权限/审计等权威逻辑归 Go 后端。
5. **按阶段提交**：每阶段跑 lint / typecheck / test / build，如实报告结果，不得声称未运行的检查已通过。
6. **组件化与一致性**：统一 Tokens、基础组件、业务组件、Section Registry；禁止每页自造样式。
7. **动态内容必须可运营**：固定模板 + 固定 Slot + 可配置 Section 实例 + 结构化内容引用 + 真实业务数据 + Draft/Preview/Publish；不做任意代码型拖拽装修器。
8. **渐进式实现**：第一版以标准商品、人工选品、标准模块组合、2D 预览为边界。
9. **未知信息不猜测**：缺失即列阻塞项与假设，可用明确标识的 Mock 完成界面开发，但不得把 Mock 当作真实能力。
10. **保持文档同步**：每阶段更新 README、`.env.example`、API 契约、数据模型、测试说明、已知限制；关键决策写入 `decisions/`。

### 7.1 每阶段必须交付

- 改动文件清单与关键实现说明；
- 已运行命令及**实际**结果（lint / typecheck / test / build）；
- 页面验证说明或截图；
- 未完成事项、阻塞项、风险与下一阶段计划；
- **真实数据与 Mock 数据的边界说明**。

## 8. 与 Ark 平台的关系

| 维度 | 结论 |
|---|---|
| 平台能力复用 | 认证、文件、通知、审计等底座能力（若后续需要）复用 `backend-service/app/platform/service` |
| 新增后端 | 本阶段**不做**。后续若需要，先在 [11-open-items](11-open-items.md) 登记契约，再走 `docs/architecture/4-1` 接入规范 |
| 管理后台 | 复用现有 `frontend-service/apps/web-antd-admin`，**不**在 Nuxt 站点内实现真实运营后台 |
| 端产物 | 公开 Web 站点，独立于 Vben 管理端与 mobile-desktop 端产物 |
