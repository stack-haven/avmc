# Ark Tech Platform 整合决策记录

本文档记录 Ark Engine 方案并入当前系统后的最终决策。它不是待评审合并方案，而是已经生效的文档口径。

## 决策

项目整体更名为 **Ark Tech Platform**。

原 Ark Engine 方案不再作为并行架构存在，其中有价值的设计已整合为 Ark Tech Platform 的平台分层：

- Ark Platform Foundation：当前多租户技术底座能力。
- Ark Business Platform：产品注册、客户运营、订阅计费、渠道、佣金。
- Ark Product Services：GEO Engine、AI Agent Management、App Version Management 和后续业务产品。

原始 Ark Engine 文档已归档到 `docs/archive/architecture-ark-source`，仅用于追溯设计来源。

## 决策原因

直接保留“Ark Tech Platform”和“Ark Engine”两套口径，会导致后续开发时反复判断哪个文档是当前事实来源。统一命名为 Ark Tech Platform 后，文档和代码迭代可以围绕一套平台模型推进：

- 当前代码继续保持稳定可运行。
- Ark Engine 的产品注册、业务平台、商业化能力被吸收到中长期路线。
- 不需要立即重写 Go package、Proto package、数据库表和前端 package。
- Codex 代理读取文档时不再需要识别“候选方案”和“当前方案”。

## 保留的 Ark Engine 设计

以下内容已经并入当前架构：

- 多产品 SaaS 平台分层。
- 产品注册中心。
- 产品菜单、权限、套餐、配额、开通表单的注册思想。
- 客户开通、客户运营、托管代运营。
- 订阅、计费、账单、用量和资源限制。
- 渠道代理、销售归属和佣金结算。
- API 边界、安全边界、租户隔离、高风险操作确认。
- 从单机部署到可扩展部署的演进路线。

## 不直接照搬的内容

以下内容不作为当前立即实现规则：

- 不强制迁移到 PostgreSQL/RLS。
- 不强制立即引入 Kong/APISIX 等独立 API Gateway。
- 不强制立即引入独立搜索、独立观测平台或独立计费服务。
- 不使用 Ark 原文中的 Node/BullMQ/Nuxt 等建议替换当前 Go/Kratos/Vben 工程基线。
- 不一次性实现 Billing、Channel、Commission、Customer Operations 全部能力。

## 当前执行策略

继续采用 Go/Kratos 大仓模式，按模块化服务边界优先推进：

- 平台基础能力优先进入 `backend-service/app/platform/admin`。
- AI/chat 通用能力保留在 `backend-service/app/ai/service`。
- `backend-service/app/version/service` 继续冻结，恢复前必须复审。
- 产品服务必须先在 `docs/services` 定义，再进入产品需求和代码实现。
- 达到独立部署、独立扩缩容、独立公共 API、独立数据生命周期或清晰业务域边界时，再评审拆服务。

## 评分复盘

本次整合采用“Ark 目标设计 + 当前工程基线”的方案。按正确与安全、稳定可运行、可规模化、可扩展与平台化、长期可演进评估，该方案综合评分最高。

| 方案 | 总分 | 结论 |
| --- | ---: | --- |
| 直接用 Ark Engine 替换当前底座 | 7.47 / 10 | 目标完整，但范围过大、技术栈不贴合当前实现 |
| 只保留当前底座并改名 | 8.40 / 10 | 短期稳定，但平台产品化能力不足 |
| Ark 目标设计 + 当前工程基线 | 8.96 / 10 | 推荐，兼顾稳定性和长期平台化 |
