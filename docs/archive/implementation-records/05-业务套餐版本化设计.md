# 业务套餐版本化设计

日期：2026-06-29
状态：实施中
范围：多租户菜单权限套餐

## 1. 问题

当前套餐直接维护菜单关系。每次修改都会覆盖原关系并立即影响全部绑定租户，存在以下风险：

- 无法确认租户曾经使用的权限集合。
- 无法区分套餐元数据修改和权限内容发布。
- 权限缩减或扩大后无法可靠回滚。
- 所有租户只能被动跟随，不能为重要租户固定稳定版本。
- 缓存虽然会失效，但缺少与变更对应的业务版本。

## 2. 模型

### 2.1 套餐

`MenuPermissionGroup` 只保存名称、编码、状态、描述等元数据，并引用当前发布版本。

### 2.2 套餐版本

`MenuPermissionGroupVersion` 是不可变权限快照：

- 套餐内递增版本号。
- 菜单 ID 快照。
- 状态：已发布、已取代。
- 变更说明、创建人、发布人、发布时间和生效时间。

已发布版本不得修改或删除。所谓回滚，是复制目标历史版本并发布一个更大的新版本号。

### 2.3 租户绑定

`TenantPermissionGroup` 增加：

- `version_id`：当前租户实际使用的套餐版本。
- `auto_upgrade`：是否跟随套餐最新发布版本。

新绑定默认跟随最新版。固定版本后，后续套餐发布不会改变该租户权限，直到显式恢复跟随或指定其他版本。

## 3. 发布规则

- 创建套餐时，初始菜单同时形成版本 `1`。
- 兼容现有管理页面：修改套餐菜单时自动发布下一个版本；仅修改名称、描述等元数据不产生新版本。
- 发布新版本后，只更新 `auto_upgrade = true` 的租户绑定。
- 套餐状态停用仍会使所有版本整体失效。
- 版本菜单只允许引用已存在菜单；菜单自身停用后仍从最终有效权限中过滤。
- 事务提交后，刷新受影响租户缓存版本。

## 4. 回滚与租户固定

- 回滚发布不修改历史记录，而是使用历史版本菜单创建新版本。
- 租户可固定套餐任一已发布版本。
- 恢复跟随时立即切换到套餐当前版本。
- 租户固定或恢复跟随后，只刷新该租户缓存。

## 5. 定时生效边界

版本保留 `effective_at`，首期只接受当前或过去时间并立即发布。未来时间的可靠发布必须具备：

- 持久化任务、抢占锁和幂等执行。
- 多实例下只执行一次。
- 失败重试、死信、监控和人工补偿。

这些能力由 P1 统一异步任务中心提供。在任务中心完成前拒绝未来时间，不能用单进程定时器伪装可靠调度。

## 6. 兼容迁移

- 现有套餐菜单关系作为当前权限镜像保留，便于旧接口兼容。
- 迁移或 mock 初始化为现有套餐生成版本 `1`。
- 没有 `version_id` 的历史租户绑定临时回退到套餐当前菜单；初始化完成后补齐版本引用。
- 所有新写入必须同时维护版本和当前权限镜像。

## 7. 验收标准

- 创建套餐后存在不可变版本 `1`。
- 菜单变化发布新版本，元数据变化不产生新版本。
- 跟随最新版租户自动切换，固定版本租户保持原权限。
- 回滚会产生更高版本号，历史版本内容不变。
- 套餐发布、租户固定和恢复跟随后对应缓存失效。
- 并发发布不能产生重复版本号。
